# Structured execution and progress evidence

Use for complex academic deliverables, improvements to AI-assisted workflows, and evidence-based reflections. Keep records in the conversation unless file output is requested. This reference does not expand the skill into a general video generator or grant permission to upload, publish, install, or archive material.

## Adapt the structure

Start from the user's goal and actual materials. State only the missing facts that affect the next action. For a simple grammar correction, preserve meaning and flag substantive ambiguity; do not launch project coordination, source research, or independent review by default.

For multi-stage tasks, establish a compact task brief:

- Deliverable and audience; scope and output format.
- Available inputs and their access scope; missing inputs.
- User requirements, including assessment AI rules when supplied. If rules are unknown, do not assert permission; continue permitted preparation and identify the uncertainty before dependent work.
- Quality criteria and what observable result would satisfy each.
- Stages and dependencies, tools available, and decisions reserved for the author.

Reuse the execution units in project-coordination.md rather than maintaining a second task tracker. Use shared record fields consistently, but adapt stages and checks to literature reading, writing, figures, or a research presentation.

At a consequential stage boundary, compare the output with the brief before using it downstream. Check meaning and evidence, not merely whether the tool returned a file. Continue routine reversible checks autonomously. Ask the author only when an unresolved choice changes their position, a required input is missing, or authorization is genuinely absent.

If a check fails, identify the failure and revise the affected stage. After a targeted correction, recheck dependent outputs. Do not repeat the same ineffective operation indefinitely; if no new information supports another attempt, report the narrow blocker and continue independent work.

For lengthy work, keep a short checkpoint in the current context: current artifact/version, accepted decisions, verified sources, unresolved issues, and next action. Re-read the relevant checkpoint and original requirements after interruption. A checkpoint supports continuity; it does not guarantee memory, accuracy, or cross-chat persistence.

## Make constraints operational

Specify what may be changed, what requires evidence, and what must remain uncertain. For scientific statements, follow evidence-and-citations.md. For an academic pitch, separate scientific claims, narrative choices, visual prompts, generated assets, and final assembly. Use appropriate available tools for production. Record which stages were automated and which the user performed; do not call a workflow fully automated merely because prompts were generated automatically.

Tool configuration and instructions are not execution evidence. Report capability states separately:

| State | Minimum basis |
| --- | --- |
| Designed | An inspectable instruction/template specifies the behavior |
| Executed | An actual action or output is available, with its task/version |
| Checked | A stated criterion was applied to that output, with result and limits |
| Improvement demonstrated | Comparable evidence supports a specific change in performance |

Do not automatically promote one state to the next. A schema check does not validate a scientific claim, and fluent AI output does not establish the author's mastery.

## Record revisions and verification

When evaluation is in scope, use a compact record for each selected task:

| Field | Record |
| --- | --- |
| Identity | Task ID, actual date or unknown, domain, output/version |
| Initial approach | Initial prompt/workflow and an accessible output or honest summary |
| Observed problem | Specific mismatch, unsupported statement, ambiguity, or failure |
| Revision | What changed and why; distinguish prompt, process, and manual edits |
| Check | Criterion, claim/source locator or other evidence, result, unresolved limits |
| Outcome | What improved, did not improve, or cannot be compared |
| Human contribution | Decisions, verification, corrections, and external manual steps |

Use existing source records rather than duplicating them. For source verification, identify the claim and the actual supporting or contradicting passage, access scope, and decision. Two references listed beside an answer do not prove two-source verification; assess relevance and whether sources provide independent support where that matters.

Use task-required source counts only when actually specified. Do not impose a universal two-source rule on grammar editing, visual styling, or other non-factual work. If the user's original learning goal required two sources per task, keep that commitment visible and report exceptions instead of silently removing it.

## Measure learning without inventing it

Separate activity measures (tasks attempted, revisions, time, course modules) from quality measures (supported claims among checked claims, task criteria met, errors found and corrected, unresolved errors). State denominators and sampling scope for rates. Fewer detected errors alone may reflect weaker checking. Time savings are meaningful only when task difficulty and quality are reasonably comparable.

Select a small number of measures relevant to the user, rather than imposing every metric. A prospective baseline can use an initial task or a short explanation exercise if the user wants it. Retrospective records can support a limited comparison, but label reconstructed timelines and missing baselines. Do not generate historical measurements from recollection or imply that today's revised skill was used earlier.

For skill-development reflection, map original commitment -> actual action -> evidence -> result -> interpretation -> next step. Keep original and revised goals distinct. Explain partial achievement without reframing it as completion. Offer interpretations as proposals until the author confirms them; do not infer the author's beliefs from AI-written prose.

Distinguish course completion certificates, course progress screenshots, practice artifacts, and performance comparisons. A skill file is a practice/design artifact, not a certificate. Check the supplied assessment for mandatory attachments; do not invent completion, issue credentials, or substitute an unrelated certificate without explaining its relevance and limitations.

## Delivery

Report the actual output, meaningful changes, checks performed, and remaining gaps. For a learning reflection, help the author connect evidence to their own interpretation; do not turn process records into claims of improved cognition. For workflow updates, identify which capabilities were implemented and which have only been specified. Persist project records only under the existing project-operations.md rules; keep personal cognitive state out of the project archive.
